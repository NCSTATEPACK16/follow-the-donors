# v1.2: the map that is the law, and the loose ends

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers:subagent-driven-development` (recommended) or
> `superpowers:executing-plans` to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** stop drawing 173 districts on a map that is no longer the law, and
close the pipeline loose ends v1 left open. v1.1 (party layer, zoom tiers,
map-first layout, Netlify guard) is built. §0 records it and what it still owes.

**Architecture:** no new dependencies and no new renderer. Redrawn geometry
enters through the one door that already exists for it,
`reference/district_overrides.csv` → `scripts/_districts.py` →
`05_districts.py`. That door has a status but, today, **no geometry path**:
see Task 1. Everything downstream (06, 07, 09, 10, the app) keys on
`district_geoid` and needs no change beyond re-running.

**Tech Stack:** DuckDB (spatial) + Python; Vite + React + TypeScript; WebGL2
halftone (`web/src/lib/plate.ts`); Playwright harness (`web/check.mjs`).

**Read `CLAUDE.md` first. Its invariants are binding and this plan does not
restate them all.**

## Global Constraints

- **`legal_status` decides which map governs, never the file on disk.**
  MO and VA enacted maps that were then blocked, so `cd119` governs there. A
  shapefile for either, sitting in `data/`, must not change a single pixel.
  `_districts.map_status()` already encodes this, and Task 1 must not add a
  second code path around it.
- **Only `enacting_authority` provenance is good enough to DRAW from.** The
  header of `district_overrides.csv` says so; `_districts._validate()` does
  not enforce it. Task 1 makes it enforced.
- **The four `map_status` values are never collapsed.** A state moves from
  `cd119_superseded` to `override_applied` only when its geometry is drawn.
  It never moves to `cd119_current`.
- **All IDs are VARCHAR.** A redrawn plan's district numbers arrive as
  whatever the legislature typed: `"1"`, `"01"`, `1`, `"District 1"`.
  Normalise them to the two-character `cd` (`'00'` for at-large) at load.
  Never cast through int.
- **Every acceptance check must be seen to fail.** Run it against the code
  before the fix and watch it fail.
- **Build before you verify.** `node web/check.mjs` runs against `web/dist`.
- **No model name** in commits, docs or code.

**Verification, every task:**

```bash
.venv/bin/python -m pytest -q          # 100 passed, 7 skipped at the start of this plan
cd web && npm test && npm run build    # 28 passing
cd .. && node web/check.mjs            # on real data: all green (see §0 for the fixture caveat)
```

## Task 1: a geometry path for overrides (no network needed)

**Why first:** it's the only part of this plan that is pure code. It also
closes a latent lie. `build_districts()` reads `districts_raw` from `cd119`
unconditionally (`05_districts.py:114`), and `map_status()` returns
`override_applied` whenever `geometry_source` is non-empty
(`_districts.py:149`). So filling in one CSV cell today would label a state
"we drew the new map" while still drawing the old one. Task 2 must not be
possible to do half-way.

- [ ] **Step 1: failing tests** in `tests/test_districts.py`:
  - An override row with `geometry_source` set and `provenance_kind =
    documentary` raises in `load_overrides` ("documentary is good enough to
    SAY a state redrew, not to DRAW it").
  - `normalise_cd("1") == normalise_cd("01") == "01"`, `normalise_cd("AL")
    == normalise_cd("0") == "00"`, and `normalise_cd("District 12") == "12"`.
    Anything else raises; never guess.
  - On a DuckDB fixture (two tiny squares for a fake state `ZZ` in cd119, two
    different squares in an override shapefile written with `ST_Write` to
    `tmp_path`), `build_districts` with `ZZ` `in_effect` + `geometry_source`
    draws the override squares, keeps the `district_geoid` values
    `statefp || cd`, and sets `map_status = override_applied`.
  - The same fixture with `ZZ` `blocked` and the same file on disk draws the
    **cd119** squares, with `map_status = cd119_contested`. This is the MO/VA
    guard.
  - An override whose district count differs from cd119's raises.
    Apportionment is fixed until 2032, so a count mismatch means the wrong
    file, not a new map.

  Run them and watch each one fail.

- [ ] **Step 2: code.**
  - `_validate`: `if ov.geometry_source and ov.provenance_kind !=
    "enacting_authority": raise`.
  - `normalise_cd(raw) -> str` in `_districts.py`.
  - `load_override_geometry(con, state, path, statefp)` creates a temp table
    `(statefp, cd, district_geoid, district_name, congress, geom)`. Set
    `congress` to the string `'override'` rather than a Congress number that
    would be invented. Reproject to cd119's CRS (EPSG:4269; read it off the
    cd119 layer, don't assume it) with `ST_Transform`.
  - In `build_districts`, after `districts_raw` is loaded: for each state
    where `D.map_status(...) == MAP_OVERRIDE_APPLIED`, `DELETE` its rows and
    `INSERT` the override's. Call `map_status()` itself; never re-test
    `legal_status` here.
- [ ] **Step 3:** tests pass; `pytest -q` shows 100 + new passed, 7 skipped.
- [ ] **Step 4: commit.** "Overrides can carry geometry, and only an
      in-effect, enacting-authority map is drawn".

**Downstream, for the record:** `build_crosswalk` intersects ZCTAs with
`districts_raw`, and 07 reads `districts_raw` for the artifact
(`07_artifacts.py:126`). Both pick up the swap with no change, which is why
the swap belongs in `districts_raw` and not later.

**Open question for the user before Task 2 lands:** `districts_raw` is shared
by both cycles. With an override applied, **2024** money would be drawn on a
2026 map. That is already true in kind (2024 was fought on 118th-Congress
maps, and cd119 differs from those too), but an override makes it worse in
the nine states. The two options: (a) apply overrides to the 2026 cycle only,
which means a per-cycle `districts_raw`; or (b) accept it and say so on the
2024 plate. Recommend (a), and ask first.

## Task 7: R2 + Worker, or Netlify only (a decision, not code)

`ROADMAP.md` lists this as open. The facts that bear on it:
- The live site serves data from Netlify's own origin, and `worker/` has
  never been deployed. No R2 bucket exists and nothing has been spent.
- With the v1.1 guard, a Netlify build without data fails instead of
  publishing an empty map. That removes the strongest argument for moving
  data off the site's origin.
- The artifact set is ~100 MB. R2's appeal is `immutable` cache headers on
  versioned names, and Netlify can set the same headers on `/data/*` in
  `netlify.toml`.

Recommend **Netlify only**, with `/data/*-v1.*` served `immutable,
max-age=31536000` and the unversioned sidecars at 1 hour, matching
`CLAUDE.md` §Publishing. Delete `worker/` rather than letting it rot, and
update `CLAUDE.md`'s $0-infrastructure note. **The user decides**: put the
recommendation to them and act on the answer.
